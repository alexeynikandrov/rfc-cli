## Problem

Команда `rfc-cli view N` выводит «сырой» Markdown в stdout. Для комфортного чтения в терминале приходится вручную прогонять вывод через внешний рендерер, например:

```sh
rfc-cli view 0001 | mdt
```

где `mdt` — терминальный рендерер Markdown.

Это неудобно:

1. Нужно каждый раз помнить и дописывать пайп `| mdt`.
2. Нет единого способа задать предпочитаемый рендерер один раз (по аналогии с `$EDITOR` для команды `edit`).
3. Поведение `view` и `edit` асимметрично: `edit` уже умеет запускать внешнюю программу из переменной окружения, а `view` — нет.

Команда `edit` (RFC-0003) уже реализует нужный паттерн: она берёт программу из `$EDITOR` и запускает её через `std::process::Command`. Логично дать `view` аналогичную возможность.

## Goal

Дать команде `view` возможность автоматически отображать содержимое RFC через внешний рендерер Markdown, заданный переменной окружения, по аналогии с тем, как `edit` использует `$EDITOR`. При этом сохранить простой способ получить сырой Markdown через флаг `--raw`.

### Requirements

1. Команда `view` должна читать имя внешнего рендерера из переменной окружения `RFC_VIEWER`.
2. Если переменная `RFC_VIEWER` **не задана** (или пуста) — команда должна вести себя как раньше: печатать содержимое RFC в stdout. Это гарантирует обратную совместимость и работоспособность пайпов вида `rfc-cli view N | mdt`.
3. Если переменная `RFC_VIEWER` задана — команда должна запустить указанную программу и передать ей полное содержимое RFC-файла на стандартный вход (stdin).
4. Значение `RFC_VIEWER` может содержать имя программы с аргументами (например, `RFC_VIEWER="mdt"` или `RFC_VIEWER="glow -"`). Строка разбивается по пробелам: первое слово — исполняемый файл, остальные — аргументы.
5. Команда должна поддерживать флаг `--raw`. Если флаг указан — команда печатает сырой Markdown в stdout **вне зависимости** от значения `RFC_VIEWER` (то есть `RFC_VIEWER` игнорируется, рендерер не запускается). Это нужно для пайпов и отладки, когда рендерер настроен глобально, но в конкретном вызове требуется исходный текст.
6. Существующее поведение по остальным пунктам сохраняется:
   - номер можно указывать с ведущими нулями или без (`view 1` == `view 0001`);
   - если RFC не найдено — ошибка `Error: RFC-NNNN not found.`
7. Код выхода:
   - `0` — при успешном выводе/рендере;
   - `1` — при ошибке (RFC не найдено, не удалось запустить рендерер, рендерер завершился с ошибкой).
8. Если рендерер не удалось запустить (например, программа не найдена) — команда должна выводить понятную ошибку: `Failed to launch viewer '<cmd>': <reason>`.
9. Все сообщения программы — на английском.

## Design

### CLI

Подкоманда `view` в `src/cli.rs` получает новый булев флаг `--raw`:

```rust
/// View RFC contents
View {
    /// RFC number
    number: String,
    /// Print raw Markdown to stdout, ignoring RFC_VIEWER
    #[arg(long)]
    raw: bool,
},
```

Диспетчер в `src/main.rs` пробрасывает флаг: `commands::view::execute(&project_root, &number, raw)`.

### Команда

Файл: `src/commands/view.rs`. Логика расширяется:

```rust
use std::env;
use std::fs;
use std::io::Write;
use std::path::Path;
use std::process::{Command, Stdio};

use crate::rfclib::rfc;

pub fn execute(project_root: &Path, number: &str, raw: bool) -> Result<(), String> {
    let normalized = rfc::normalize_number(number)?;
    let path = rfc::rfc_path(project_root, number)?;

    if !path.exists() {
        return Err(format!("RFC-{} not found.", normalized));
    }

    let content = fs::read_to_string(&path)
        .map_err(|e| format!("Failed to read {}: {}", path.display(), e))?;

    // --raw форсирует сырой вывод и игнорирует RFC_VIEWER
    if raw {
        print!("{}", content);
        return Ok(());
    }

    // RFC_VIEWER задан и непуст — рендерим через внешнюю программу
    match env::var("RFC_VIEWER") {
        Ok(viewer) if !viewer.trim().is_empty() => {
            render_with_viewer(&viewer, &content)
        }
        _ => {
            print!("{}", content);
            Ok(())
        }
    }
}
```

Функция запуска рендерера:

```rust
fn render_with_viewer(viewer: &str, content: &str) -> Result<(), String> {
    let mut parts = viewer.split_whitespace();
    let program = parts.next().unwrap(); // непустая строка гарантирована вызывающим кодом
    let args: Vec<&str> = parts.collect();

    let mut child = Command::new(program)
        .args(&args)
        .stdin(Stdio::piped())
        .spawn()
        .map_err(|e| format!("Failed to launch viewer '{}': {}", viewer, e))?;

    if let Some(mut stdin) = child.stdin.take() {
        stdin
            .write_all(content.as_bytes())
            .map_err(|e| format!("Failed to write to viewer '{}': {}", viewer, e))?;
    }

    let status = child
        .wait()
        .map_err(|e| format!("Failed to wait for viewer '{}': {}", viewer, e))?;

    if !status.success() {
        return Err(format!("Viewer '{}' exited with error", viewer));
    }

    Ok(())
}
```

### Замечания

- `view` не трогает индекс и не изменяет файлы — это read-only команда, поведение относительно индекса не меняется.
- Разбор `RFC_VIEWER` по пробелам — простое и предсказуемое решение; сложный парсинг с кавычками не требуется для типовых значений (`mdt`, `glow -`, `bat -l md`).
- Симметрично `edit`: там программа берётся из `$EDITOR` и получает путь к файлу аргументом; здесь программа берётся из `RFC_VIEWER` и получает содержимое через stdin (типичный контракт Markdown-рендереров вроде `mdt`).

## Alternatives

1. **Использовать стандартную `$PAGER`.**
   Недостаток: `$PAGER` обычно указывает на `less`/`more` — постраничные просмотрщики, а не Markdown-рендереры. Смешивание семантики привело бы к неожиданному поведению у пользователей с настроенным `$PAGER`.

2. **Управлять рендерингом только флагом `--pager <cmd>` / `--render`, без env-переменной.**
   Недостаток: избыточно для основного сценария (пользователь хочет задать рендерер один раз). Env-переменная повторяет уже привычный паттерн `$EDITOR` из `edit`. Флаг `--raw` при этом остаётся полезным как разовое исключение — принудительный сырой вывод в обход настроенного `RFC_VIEWER`.

3. **Передавать содержимое рендереру аргументом-файлом, а не через stdin.**
   Недостаток: не все рендереры принимают путь; передача через stdin — более универсальный контракт и совпадает с тем, как пользователь уже вызывает `rfc-cli view N | mdt`.

4. **Оставить всё как есть (`view N | mdt`).**
   Недостаток: не решает проблему — сохраняется ручной пайп и асимметрия с `edit`.

## Migration

Миграция не требуется. Изменение обратно совместимо: при отсутствии `RFC_VIEWER` поведение `view` не меняется.

Шаги реализации:

1. Расширить `src/commands/view.rs`: чтение `RFC_VIEWER`, флаг `--raw`, запуск рендерера через stdin, fallback на stdout.
2. Добавить флаг `--raw` в `src/cli.rs` и пробросить его через `src/main.rs`.
3. Добавить тесты:
   - `view` печатает содержимое в stdout, когда `RFC_VIEWER` не задана (регресс существующего поведения);
   - `view` запускает рендерер и передаёт ему содержимое, когда `RFC_VIEWER` задана (например, `RFC_VIEWER="cat"`);
   - `view --raw` печатает сырой Markdown в stdout, даже когда `RFC_VIEWER` задана;
   - `view` возвращает ошибку, если рендерер не удалось запустить (несуществующая программа);
   - `view` возвращает ошибку `Error: RFC-NNNN not found.` для несуществующего RFC.
4. Обновить документацию: секции «Environment Variables» в `README.md` и `README_ru.md` (добавить `RFC_VIEWER`) и описание флага `--raw` у команды `view`.
5. Привязать файлы к RFC: `rfc-cli link 0009 src/commands/view.rs src/cli.rs src/main.rs tests/integration_test.rs`.

## Test Plan

- Без `RFC_VIEWER`: `rfc-cli view N` печатает сырой Markdown в stdout (обратная совместимость, пайпы работают).
- С `RFC_VIEWER="cat"`: содержимое проходит через рендерер и выводится.
- С `RFC_VIEWER="cat"` и флагом `--raw`: рендерер игнорируется, выводится сырой Markdown.
- С `RFC_VIEWER` = несуществующая команда: ошибка запуска, код выхода `1`.
- Несуществующий RFC: ошибка `Error: RFC-NNNN not found.`, код выхода `1`.
- Значение с аргументами (`RFC_VIEWER="glow -"`): корректный разбор программы и аргументов.
